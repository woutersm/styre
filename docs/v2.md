
# styre v2: handoff

## Purpose

styre v2 turns styre from a gatekeeper around one local agent into a system that plans, builds, unblocks and reviews. One local model, Qwen3.8-27B, does most of the work. A frontier model, Claude run through Claude Code, makes the few decisions that need judgement, at fixed points.

This doc is the handoff for building it. The reader is the implementer, a person working with Claude Code, who knows v1 or has its repository open. It sets the premises, the principles, the architecture, the interfaces, and the order to build in, starting with a benchmark of v1 as it stands. It leaves code-level choices to the implementer.

### Where v1 stands

v1 is a standard-library Python CLI. It runs a phased design through the pi coding agent, one fresh process per step, then runs the gate itself, rejects diffs that skip or delete tests, and commits one phase per commit. It calls no model and makes no judgement. Every mechanism came from a measured failure, listed in `docs/lessons.md`.

v1 assumed the builder's claims could not be trusted. Its own evidence points elsewhere. In the interface eval the builder kept the contract in 30 of 30 trials, and when the gate could not pass honestly it reported BLOCKED every time. The expensive failures in `lessons.md` were about context and missing information:

- a restarted agent spent 80 minutes reading the tree again;
- every step of one phase spent about 12 `python -c` calls learning an unfamiliar library;
- one compaction prefilled 48k tokens and took 8.5 minutes;
- an interactive setup was 47% of every request.

v2 is built for those failures.

## New premises

Two premises change: agents act in good faith, and styre may call models. One stays: the work runs unattended on a local host, and a person approves before it starts and reviews when it ends.

| Concern | v1 | v2 |
| --- | --- | --- |
| Who decides a task is done | styre, by re-running the gate after the agent stops | the builder, with checks as its feedback; styre runs the full checks once before committing |
| Changed or skipped tests | a stop | a logged metric |
| Judgement (plan, unblock, review) | the person or an interactive assistant | roles styre calls, under written policies |
| Memory between phases | one note, one hop | a curated project memory every task can draw on |
| Model calls by styre | none | planner, advisor and reviewer runs through Claude Code, with tokens in and out logged |
| The person's role | writes the design, reads every stop, reviews | approves the plan, approves anything live, reviews the result |

### Good faith is not correctness

An honest agent can still be wrong, so checks stay. They change role: v1 used them to catch a cheating agent, v2 uses them to tell a capable one where it stands. A wrong result costs a retry, not a lost night.

The premise is also something to measure, not assume. v2 keeps two numbers from v1's guard in every run report: how often the builder said done with failing checks, and how often it removed or skipped a test. If a new model breaks the premise, those numbers show it before the commits do.

### One local model, one frontier model

The local model, Qwen3.8-27B on oMLX with Splash as its engine, costs nothing per token but spends wall-clock time. The frontier model, Claude through Claude Code, is fast and strong. styre models no cost. Every model call has a role, a typed input, a typed output and a log line with tokens in, tokens out and time.

## First principles

On a local host the scarce resources are wall-clock time and context, not tokens. Each principle below names what it requires of v2.

The reference host is an M4 Pro with 48 GB running oMLX 0.7.3, which serves Qwen3.8-27B (Unsloth GGUF UD-Q4_K_M) through Splash 1.4.0 as its external engine, with a DFlash2 draft model. It is the only local model. The host changed on 2026-10-27, after M0's baseline ran on standalone Splash with the MLX 4-bit weights; see [Reference host change](#reference-host-change-2026-10-27). oMLX 0.6.4 had hit a prefill memory guard at about 76k tokens; under Splash, standalone and inside oMLX 0.7.3, there is no ceiling up to pi's 120k window: a 103k prompt prefills at 146 tok/s, 12 minutes from a cold cache.

1. **Prefill is the hidden cost.** Every token in context is processed again on each request unless the prefix cache holds it. v2 keeps history append-only, orders every request from most stable to least stable (rules, tool schemas, task spec, then the work), and logs cached and uncached prompt tokens per request.
2. **A task must fit well inside the usable window.** The planner sizes tasks by expected peak context, aiming at about half the ceiling M0 measures, not by feature boundaries. v1's history shows why: phases spanning two toolchains peaked at 74k to 116k tokens, and 73% of them went badly.
3. **The builder should write, not research.** Each task arrives with a context pack: the files and line ranges it needs, the signatures it calls, a working example for any library new to the repo, and known traps. Building that pack once is cheaper than the builder exploring on every step.
4. **Done is executable.** Each task's acceptance criteria are tests or commands that exist before the task starts. Under the trust premise this is about precision, not policing: a smaller model hits a target it can run far more often than one described in prose.
5. **Frontier tokens go around the loop, never inside it.** The frontier model plans, writes acceptance tests, unblocks a stalled task and reviews a finished milestone. Each call is short, with a bounded input. The edit, run and fix loop stays local.
6. **One local model, one frontier model.** Qwen3.8-27B does every local job: building, picking what goes into context packs, and keeping memory. Claude, through Claude Code, plans, unblocks and reviews. With one local model there are no reloads between tasks and no routing to tune, and a stalled task goes straight to the advisor.
7. **Hours are free, but only serial hours are known.** Overnight runs can afford retries and second attempts. Running attempts in parallel only pays if the host serves concurrent requests faster in total than one at a time. On a single M4 Pro that is unmeasured, so v2 measures it before building on it.
8. **The core stays deterministic.** The orchestrator is a state machine that calls models at defined points with typed inputs and outputs. Every transition lands in the timeline, so a run can be explained from disk.

## Architecture

styre stays a deterministic orchestrator, and models fill six roles around it. Qwen3.8-27B does the work inside the task loop. Claude, through Claude Code, works before the run, when a task stalls, and at the end of each milestone.

The frontier roles run once per design, once per milestone, or when a task stalls. Nothing inside the loop waits on Claude, which keeps frontier tokens bounded.

| Role | Model | When it runs | Input | Output |
| --- | --- | --- | --- | --- |
| Planner | Claude Code | once per design, and again when review adds work | `design.md`, the repository, `memory.md` | `plan.json`, acceptance tests |
| Librarian | repository map plus Qwen3.8-27B | just before each task | the task's symbols and files, `memory.md` | context pack |
| Builder | Qwen3.8-27B in pi | each task | spec, context pack, acceptance tests | code, `progress.md`, task result |
| Advisor | Claude Code | when a task stalls | escalation | one action |
| Reviewer | Claude Code | at the end of each milestone | milestone diff, design, acceptance tests | findings |
| Curator | Qwen3.8-27B | after each commit | task notes, `memory.md` | updated `memory.md` |
| styre | none | always | everything above | processes, checks, commits, timeline |

### One run

1. `styre plan design.md` calls the planner, checks the plan against the sizing rules, and renders `plan.md`.
2. The person approves the plan. styre commits the acceptance tests to the run branch.
3. `styre run` takes tasks in dependency order. For each, the librarian builds the pack, the builder works on its starting rung with fast checks as feedback, and styre runs the full checks. On green, styre commits and the curator updates `memory.md`.
4. A task stalls when two fix rounds do not reduce its failures, when a fresh start changes neither the tree nor `progress.md` (v1's rule), or when the builder reports BLOCKED. A stalled task goes to the advisor.
5. At the end of each milestone the reviewer reads the diff. Each finding becomes a task in the graph or is dismissed with a reason.
6. At the end of the run, `styre summarize` reports the metrics, and the person reviews and merges.

### Frontier through Claude Code

Every frontier role is a `claude -p` run that styre starts as a subprocess in the target repository, the way it starts pi for the builder. Claude Code brings its own tools, so the planner and the advisor read the repository themselves instead of getting it pasted into a prompt.

- Each role passes `--output-format json` with `--json-schema`. The answer comes back in `structured_output`, next to the run's usage, which styre writes to the timeline as tokens in and out ([headless docs](https://code.claude.com/docs/en/headless.md)).
- Each role gets only the tools it needs. The planner reads the repository and writes under `tests/acceptance/`. The reviewer reads and runs `git diff`. The advisor reads, and edits only when it chooses `patch`.
- The process rules for pi apply here too: an idle timeout, a process-group kill, and a stop when a run returns no result.
- On subscription plans, `claude -p` usage draws from a monthly Agent SDK credit, separate from interactive limits, since June 15, 2026. Running out mid-run is a stop like any other.

## Artifacts and interfaces

Everything styre and its roles exchange is a file with a fixed shape, so a run can be resumed, replayed and inspected from disk. Model calls take and return JSON that styre validates; a call that returns the wrong shape gets one retry, then counts as a failed call.

| Artifact | Written by | Read by | What it holds |
| --- | --- | --- | --- |
| `design.md` | the person | planner | goal, constraints, non-goals; gates optional. A v1 design still loads: each phase becomes a task with its gate as acceptance |
| `plan.json`, rendered as `plan.md` | planner | the person, then styre | the task graph; the person approves `plan.md` before a run |
| Acceptance tests | planner | builder, styre | test files committed before their task starts |
| Context pack | librarian | builder | files and line ranges, signatures, examples, traps, memory items; capped at about 8k tokens |
| `progress.md` | builder | builder after a restart, advisor | v1's four fields: done, now, next, learned |
| Task result | builder, styre | styre, dependents | done, blocked or stalled, a reason, notes for dependent tasks |
| Escalation | styre, then advisor | styre | the stall and what was tried; the advisor's chosen action |
| `memory.md` | curator | librarian | project facts, each with the task it came from; capped in size |
| Review findings | reviewer | styre, the person | each finding becomes a new task or is dismissed with a reason |
| `timeline.jsonl` | styre | `summarize`, the benchmark | every transition and every model call with role, model, tokens in and out, cached prompt tokens, and prefill and decode seconds |

### A task

`styre.json` names the two models: `local` points at the local endpoint (oMLX) and model, and `frontier` at the Claude Code command and its flags. A plan never names a model, so the same plan runs on another host.

```json
{
  "id": "t07",
  "title": "Load reminder rules from YAML",
  "milestone": "m2",
  "depends_on": ["t03", "t05"],
  "spec": "Add rules.load(path) -> list[Rule] in src/todo/rules.py ...",
  "context_pack": {
    "files": [{"path": "src/todo/models.py", "lines": [1, 60]}],
    "signatures": ["class Rule: ..."],
    "examples": [{"library": "pyyaml", "code": "rules = yaml.safe_load(fh)"}],
    "traps": ["fixture dates are naive; keep them naive"],
    "memory": ["m12"]
  },
  "acceptance": {
    "tests": ["tests/acceptance/test_t07_rules.py"],
    "commands": ["uv run pytest -q tests/acceptance/test_t07_rules.py"]
  },
  "checks": {
    "fast": ["uv run ruff check src/todo/rules.py"],
    "full": ["uv run ruff check .", "uv run mypy src", "uv run pytest -q"]
  },
  "expected_peak_tokens": 30000,
  "max_attempts": 3
}
```

### An escalation

When a task stalls, styre sends the advisor the task, `progress.md`, the last check failures parsed into file, line and message, and a diff stat. The advisor returns exactly one action:

| Action | Effect |
| --- | --- |
| `amend` | rewrites the spec or adds to the context pack, then the task retries |
| `split` | replaces the task with smaller tasks in the graph |
| `patch` | the advisor edits the hard part itself through Claude Code; styre runs the checks and commits it, marked as written by Claude |
| `stop` | parks the task and its dependents for the person, with a one-paragraph reason |

## What carries over

Most of v1's runtime carries over unchanged, because it solved context and process problems that the new premises do not touch. What changes is everything around the builder: who plans, who decides done, and how tasks share what they learn.

| v1 mechanism | Verdict | In v2 |
| --- | --- | --- |
| pi under its own config, `--no-skills --no-mcp` | keep | unchanged; the builder harness for v2 |
| Output caps, no compaction, earlier thinking dropped | keep | unchanged; thinking removal is checked against the new cache-hit numbers |
| Fresh process per step, relay from `progress.md` at 75% | keep | the relay line comes from the task's expected peak as well as the window |
| Idle timeout, process-group kill, closed stdin | keep | plus the open TODO: a time limit per bash call |
| Empty-response detection | keep | extended to Claude Code runs |
| All check failures handed back at once | keep | failures parsed into file, line and message before they reach a prompt |
| Resumed fix round below 50% of the window | keep | unchanged |
| One commit per unit of work, on a branch | keep | one commit per task; the message says whether Claude wrote any of it |
| `timeline.jsonl`, `summarize` | keep | extended with per-call model metrics and the open TODO `summarize --compare` |
| `evals/interface.py` | keep | a regression suite for the builder contract, plus the open TODO relay scenario |
| `styre_finish` refuses DONE on red | keep | as feedback to the builder, not as a guard |
| Phases with hand-written gates | change | a task graph from the planner, with acceptance tests written before each task |
| `styre check` warnings | change | sizing rules the planner must satisfy; the two-toolchain warning becomes a hard rule |
| `notes-next.md`, one hop | change | notes travel along graph edges to dependent tasks, and lasting facts go to `memory.md` |
| `docs/decisions.md`, never read | change | folded into `memory.md`, curated and capped instead of hidden |
| Test-tampering guard | change | a metric in every report, not a stop |
| `DIRECTOR.md` rules | change | policies in code: the person approves the plan and anything live; a task stuck twice goes to the advisor |
| styre calls no model | drop | replaced by Claude Code runs at fixed points |
| Hidden held-out tests at runtime | still out | they belong in the benchmark, where they measure styre instead of gating it |
| A web viewer | still out | `summarize` and the timeline stay the way to read a run |

## Milestones

The milestones are the migration from v1 to v2, done in place in the same repository and CLI. M0 benchmarks v1 as it is today, before anything changes. v1 keeps working until M3 replaces its executor, and v1 designs still load as plans after that. Each milestone is sized as a v1 design of three to six phases, so v1 builds M0, M2 and M3, and from M4 on, v2 builds the rest of itself. There is no M1: the Claude Code runner it held is built in M2, with the planner, its first caller (decided 2026-10-25). A runner is easier to get right next to its first caller.

A milestone ends only when its check passes. The whole of v2 is built; the benchmark measures each milestone and does not decide whether it stays (decided 2026-10-25).

### Scope per milestone

1. **M0, benchmark v1.** Four designs and their reference suites, kept in a private repository because they come from private projects (styre is public). `summarize` reports requests, uncached and cached prompt tokens, the cache hit rate, and prefill and decode minutes per phase, read from pi's events; `summarize --compare A B` puts two runs side by side. `evals/bench.py` runs one benchmark design end to end and scores it; `evals/bench_report.py` reports the results by configuration: styre version, design variant, model host, model, context window and a free label, so runtimes, quants and context sizes compare as configurations. Measure Splash's usable context ceiling for Qwen3.8-27B and whether it serves concurrent requests faster in total. Run v1 on the four briefs once. v1's behaviour does not change in this milestone.
2. **M2, Claude Code runner and planner.** Before it starts, `CLAUDE.md`'s settled decisions are rewritten for v2 (styre now calls a model), approved by the person. The first phase is the runner for `claude -p` beside the pi runner: one subprocess per role call, `--output-format json` with the role's schema, usage written to the timeline, and a process-group kill at a deadline. `styre.json` names the Claude Code command. Tests use a fake `claude` on `PATH`, the way `fake_pi.py` stands in for pi. Then `styre plan design.md` turns a brief into a full v1 design: the planner reads the repository and adds, per phase, the files and line ranges, signatures, library snippets, test conventions and traps; styre refuses an answer that drops or changes a line of the brief, and commits the result for the person to read; `styre run` builds it unchanged. `bench.py --plan` benchmarks it. (Rescoped 2026-10-26 from a task graph with acceptance tests: M0 put 26 of v1's 33 missed tests and about 6 of its 8.9 hours down to the help a brief leaves out, which the full designs supplied at 98% in 4.3 hours, and about 7 tests down to a wrong reading. Acceptance tests, `plan.json` and the task graph move to M3, which is re-decided from M2's benchmark.)
3. **M3, task loop.** The executor walks the graph. The librarian resolves symbols to line ranges when each task starts. Check output is parsed into file, line and message, and notes travel along graph edges. No advisor yet.
4. **M4, advisor.** The stall rules, the advisor's four actions, and a cap on `patch` actions per design.
5. **M5, review and memory.** The reviewer runs at each milestone end. The curator keeps `memory.md`, and the librarian draws on it.
6. **M6, experiments.** Parallel attempts in worktrees, only if the host gains from concurrent requests (M0 and the oMLX probe showed it does not). A native builder loop with constrained tool calls, only if malformed tool calls or cache misses rank among the top time costs.

## How we know v2 is better

v2 is better only if it commits more correct work per night than v1, with fewer stops for the person, and with the frontier tokens it took on record. So the benchmark is built first, and v1 is measured on it before any v2 feature exists.

### The benchmark

Four designs v1 already ran, each with a reference test suite the builder never sees. The suite runs once against the committed work, after the run ends. A design is benchmarked from its **brief**: the same phases, gates and every interface the suite checks, at about 40% of the original's size, without the implementation help. v1 scored 183 of 186 reference tests on the full originals, too close to the ceiling to show an improvement.

| Design | What it covers | v1 hours on the full design |
| --- | --- | --- |
| trene | a greenfield Python CLI on libraries new to the repository | 0.97 |
| todo-rules | a feature in a large Python repository | 1.04 |
| subtasks | a feature across a TypeScript backend and its web UI | 1.61 |
| review-fixes | fixes in a TypeScript library | 0.69 |

Not covered: a port checked by golden files, and a design gated in both Python and TypeScript; both took 6 to 22 hours, past the budget.

The budget is about four to five hours per configuration: the four briefs, once each. The baseline is v1 on the briefs, run once. The full originals' scores from v1's own runs are the ceiling, at no extra cost. Run-to-run noise is measured only when a comparison is close: then the two shortest briefs run again, about two hours. If M0 shows Splash serves two requests faster in total than one, two designs run at once.

### Metrics

| Metric | Definition | What it tells us |
| --- | --- | --- |
| Correctness | share of reference tests passing on the final branch | whether the work is right |
| Autonomy | stops that needed the person, per design | whether it runs overnight |
| Tokens | tokens in and out per design, split by model and by role | what each role consumes |
| Local share | share of committed lines written by Qwen3.8-27B | whether it is still a local-model tool |
| Time | local hours per design, split into prefill, decode, tool calls and checks | where the night goes |
| Cache hits | cached prompt tokens over all prompt tokens on the local server | whether principle 1 holds |
| Sizing | each task's peak context against its expected peak | whether the planner sizes well |
| Good faith | said-done-on-red rate and test-removal rate | whether the trust premise holds |

Local share matters most for honesty. If the frontier model ends up writing most of the code, v2 is a frontier tool with a slow assistant, and the report should say so.

### Configurations

Two, on the same four briefs and the same host:

1. v1 as it is today.
2. v2, full.

No ablations: v2 is built whole, so a run with one role switched off would answer nothing that is acted on (decided 2026-10-25). Other hosts, quants and context sizes are extra configurations of either, run only when wanted.

The headline the benchmark should produce has this shape: on the reference host, v2 passes X% of held-out tests across the four briefs against Y% for v1, with Z stops for the person and W frontier tokens per design.

### M0 results (2026-10-26)

v1 (styre 0.25.0) on the four briefs, once, on the reference host: Splash, Qwen3.8-27B 4-bit, int8 KV cache, a speculative draft model, 120k context. Each design was capped at 3 hours. The raw results and the setup are in the private benchmark repository.

| Design | New tests | Kept tests | Phases | Hours (full design) |
| --- | --- | --- | --- | --- |
| review-fixes | 23/23 | 7/7 | 4/4 | 2.80 (0.69) |
| todo-rules | 17/17 | 9/9 | 5/5 | 0.81 (1.04) |
| subtasks | 38/40 | 2/2 | 4/4 | 2.25 (1.61) |
| trene | 75/106 | - | 4/6, stopped at the cap | 3.00 (0.97) |
| **Total** | **153/186 (82%)** | **18/18** | **17/19** | **8.86 (4.31)** |

- Correctness: 82% against 98% on the full designs (183/186). That leaves room to show an improvement, so the briefs stay the benchmark and no harder variant is needed.
- Where the misses are: 26 of trene's 31 are in the two phases the cap cut off (its CLI and MCP server). Both subtasks misses are one rule the brief states and the builder missed (no recurrence on a subtask or on a parent with subtasks).
- Time: the briefs took twice the full designs' hours, so one configuration costs about 9 hours, not 4 to 5. Decode was 7.2 of the 8.9 hours, and thinking was 70% of output (606k of 871k tokens; 66 to 74% per design), about 5 hours at the measured decode rate. Thinking is the largest single time cost, and prefill is not. review-fixes spent 132 of its 168 agent minutes in Phase 1 alone, peaking at 90k tokens.
- Cache hits: 97.9% of prompt tokens. Delivered rates were 148 tok/s prefill and 33 tok/s decode.
- Autonomy: one stop, trene at the cap.

What the probe measured on Splash (single requests, 128 tokens generated):

| Prompt | Prefill tok/s | Decode tok/s | Time to first token |
| --- | --- | --- | --- |
| 4k | 253 | 35.0 | 15 s |
| 16k | 239 | 30.0 | 60 s |
| 59k | 182 | 22.2 | 5.4 min |
| 86k | 159 | 19.3 | 9.0 min |
| 105k | 145 | 19.5 | 12.0 min |

- The usable ceiling is pi's 120k window, not the server: 105k ran with no memory guard. Half of it, about 60k, is the planner's target peak per task.
- Concurrency: two decode-bound requests together ran 1.12x faster in total than one, four ran 1.15x, and prefill was served one request at a time. Designs and attempts run serially on this host.
- Draft acceptance: 24 to 34% per request, 37% over the server's lifetime.

### Reference host change (2026-10-27)

The host moved from standalone Splash with `mlx-community/Qwen3.8-27B-4bit` to oMLX 0.7.3.dev2 serving `unsloth/Qwen3.8-27B-GGUF:UD-Q4_K_M` through Splash 1.4.0, same Mac, same int8 KV cache, a DFlash2 draft, 120k context. v1 (styre 0.25.0) ran the four briefs once on it, with the same 3-hour cap.

| Design | New tests | Kept tests | Phases | Hours (Splash, MLX 4-bit) |
| --- | --- | --- | --- | --- |
| review-fixes | 23/23 | 7/7 | 4/4 | 0.72 (2.80) |
| todo-rules | 17/17 | 9/9 | 5/5 | 0.56 (0.81) |
| subtasks | 38/40 | 2/2 | 4/4 | 1.42 (2.25) |
| trene | 97/106 | - | 6/6 | 2.17 (3.00, cap) |
| **Total** | **175/186 (94%)** | **18/18** | **19/19** | **4.87 (8.86)** |

- Correctness: 94% against 82%. The gain is trene, which finished all six phases inside the cap; the other three scored the same. Both subtasks misses are the same recurrence rule as before.
- trene is the clean rerun of 2026-10-27. The first UD run of trene scored 99/106 but was contaminated: in Phase 2 the builder grepped the whole benchmark folder, found the baseline run's `docs/decisions.md` for the same design under `results/`, and used its answer to the float32 rounding of pace targets. No other run read outside its own copy. `bench.py` now builds each run in a temporary directory, and the rerun, built that way, scored 97/106 in 2.17 hours: the contamination was worth two tests and six minutes.
- Time: 4.87 hours against 8.86, with the same token rates (158 tok/s prefill, 36 decode). Output fell 45% (480k against 871k tokens): fewer turns and less thinking, not faster tokens.
- Two things changed at once, the server and the weights, and each configuration ran once. The probes show the server does not change speed; which change cut the output is not measured. Running MLX 4-bit on oMLX would separate them.
- The probe, run on both weights under oMLX (single requests, 128 tokens generated), matched standalone Splash within noise: prefill 252 tok/s at 4k down to 146 at 103k, decode about 20 tok/s from 59k up. Two concurrent requests ran 0.81x to 0.91x in total, four 0.98x to 1.12x.
- From here on, this run is v1's baseline for comparisons on the reference host. The Splash run stays as the record of M0.

## Risks and open decisions

v2 adds five roles. The benchmark reports what each costs and buys, run against v1's baseline.

### Risks

| Risk | How it shows | Response |
| --- | --- | --- |
| Frontier creep: advisor patches pile up | local share falls, frontier tokens rise | a cap on `patch` actions per design, and both numbers in every report |
| The planner over-splits | many tasks far below the expected peak; process start and rule prefill dominate the time | a minimum task size; the planner merges small neighbours |
| Acceptance tests encode a wrong reading of the design | the builder stalls on a test it cannot pass honestly | the person approves test names and assertions with the plan; the builder may flag a test as wrong, and the advisor decides |
| Context packs go stale | line ranges point at code an earlier task moved | the plan stores symbols, and the librarian resolves them to line ranges when the task starts, not at plan time |
| The Agent SDK credit runs out mid-run | a `claude -p` run ends without a result | the task stops like an empty response and waits for the person; tokens per role show where the credit went |
| pi or Claude Code changes under styre | captured event fixtures stop matching | each sits behind one runner interface, and the fake-pi and fake-claude tests keep running |

### Open decisions

1. **Keep pi as the builder, or write a native loop.** Keep pi through milestone 5. A native loop would allow grammar-constrained tool calls and full control of the cached prefix. Try it only if the benchmark shows malformed tool calls or cache misses among the top time costs.
2. **Standard library only.** Keep it. pi and Claude Code run as subprocesses. The librarian and the curator make single completions, not agent runs, so styre calls the local server's OpenAI-compatible endpoint (oMLX) directly with `urllib`.
3. **Subscription or API key for Claude Code.** Without `--bare`, `claude -p` uses the subscription login, but it also loads `~/.claude` and the repository's `CLAUDE.md`, hooks and skills. That is the inherited-setup problem v1 measured at 47% of a request, though a target repository's own `CLAUDE.md` is context the planner wants. With `--bare` it starts clean but needs an `ANTHROPIC_API_KEY`. Start on the subscription, measure in M2 what the inherited setup adds to tokens in per call, and switch to `--bare` if it is large.
4. **Who builds context packs.** A deterministic repository map, from Python's `ast` and ctags for other languages, plus Qwen3.8-27B to pick what goes in. Claude contributes only at plan time, for examples of libraries new to the repository.
5. **How much of the plan the person approves.** The whole plan, acceptance tests included, for the first runs. Milestones only, once acceptance tests prove reliable on the benchmark.
